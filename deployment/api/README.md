# deployment/api/: the model API

The Phase 3 model service: a **FastAPI** app that serves the project's two final models over HTTP/JSON. It is
deployed on **Render** and the Streamlit app in `deployment/model_app/` is its frontend. The pattern follows the
course's deployment lesson (L6): models trained in the notebooks, served by an API that loads them once, called by a
separate user interface.

```
notebooks + build_models.py ──► models/*.joblib ──► FastAPI on Render (this folder) ◄── HTTP/JSON ── Streamlit app
      (train, check)              (GitHub)          loads once, validates,              ◄── batch_score.py (bulk)
                                                    predicts, logs                      ◄── any script or notebook
```

| Model | Problem | Role |
|---|---|---|
| `freight_forest.joblib`: RandomForest regressor on log(1 + freight), 200 trees | Problem 1, fair freight | the fair freight of an item; test MAE R$ 5.40 (24.7% of mean freight) on the latest 20% of items |
| `freight_ridge.joblib`: Ridge (alpha 10) on log(1 + freight) | Problem 1 | second opinion on unusual charges; test MAE R$ 6.12 |
| `late_logit.joblib`: plain LogisticRegression | Problem 2, late delivery | risk ranking for the daily review queue; test lift 2.00 |

**Live:** https://team5-olist-api.onrender.com (interactive documentation at
https://team5-olist-api.onrender.com/docs). On Render's free tier the service sleeps after 15 minutes without traffic,
and the first request then takes 30 to 60 seconds.

## Endpoints

| Method | Path | What it returns |
|---|---|---|
| GET | `/` | health: status, version, model build date, uptime |
| GET | `/model-info` | the models, their inputs, test results, the unusual-freight rules, price bands, tariff, validation ranges and drift method |
| POST | `/freight/predict` | one item: fair freight (forest), Ridge second opinion, quote range, simple tariff; with a charge, the unusual-freight check under both rules |
| POST | `/freight/batch` | the same for up to 5,000 items |
| POST | `/late/predict` | one order: risk score, percentile among test-window orders, on the review list or not, each input's log-odds contribution, suggested follow-up |
| POST | `/late/batch` | the same for up to 5,000 orders |
| GET | `/logs/summary` | monitoring totals from the inference log: traffic, rejected inputs, drift rate and inputs, unusual-charge rate, review-list share, follow-ups, latency |
| GET | `/docs` | interactive documentation generated by FastAPI from the Pydantic schemas (try any endpoint in the browser) |

Every prediction response carries `request_id`, `timestamp` and `latency_ms`, plus `notes` (how the inputs were
derived, for example from a zip code) and `drift_warnings` (inputs unlike the training data).

The examples below use `API=https://team5-olist-api.onrender.com`; for a local server use `API=http://localhost:8000`.

### POST /freight/predict (Problem 1)

Request fields (units R$, kg, cm³, km):

| Field | Required | Rule |
|---|---|---|
| `price` | yes | > 0, ≤ 100,000 |
| `weight_kg` | yes | ≥ 0, ≤ 500 |
| `volume_cm3` | yes | > 0, ≤ 5,000,000 (length × width × height) |
| `seller_state`, `customer_state` | yes | one of the 27 two-letter state codes (case-insensitive) |
| `seller_zip`, `customer_zip` | no | a CEP (`01310-100`) or its first five digits (`01310`); places the party more precisely than the state centre. If the zip lies in another state, the zip's state is used (with a note) |
| `distance_km` | no | 0 to 5,000. Leave it out to derive it from the zip codes (or the state centres); send `null` to mark it unknown, as for records whose zip is not in the Olist table (the models then use the training median, as in training) |
| `category` | no | an Olist category such as `bed_bath_table`; default `unknown`. Unseen categories get a drift warning and are treated as rare |
| `n_items`, `n_sellers` | no | items and sellers in the order, default 1; `n_sellers` ≤ `n_items` |
| `freight_value` | no | the freight charged (≥ 0). When given, the response checks whether it is unusual |
| `id` | no | your reference, echoed back |

```bash
curl -X POST $API/freight/predict -H "Content-Type: application/json" -d '{
  "id": "listing-1", "category": "bed_bath_table", "price": 120, "weight_kg": 1.5, "volume_cm3": 9000,
  "seller_state": "SP", "customer_state": "RJ", "seller_zip": "01310", "customer_zip": "20040",
  "freight_value": 35}'
```
```python
import requests
item = {"id": "listing-1", "category": "bed_bath_table", "price": 120, "weight_kg": 1.5, "volume_cm3": 9000,
        "seller_state": "SP", "customer_state": "RJ", "seller_zip": "01310", "customer_zip": "20040",
        "freight_value": 35}
r = requests.post(f"{API}/freight/predict", json=item, timeout=90)
r.raise_for_status()
p = r.json()
print(f"fair R$ {p['fair_freight']:.2f}, quote R$ {p['quote_low']:.0f}-{p['quote_high']:.0f}, "
      f"verdict {p['check']['rules']['band']['verdict']}")
```
Response (abridged):
```json
{
  "request_id": "req_20261029_064649_5622d3", "timestamp": "2026-10-29T06:46:50+00:00", "latency_ms": 41.3,
  "id": "listing-1",
  "fair_freight": 18.34, "fair_freight_ridge": 17.89,
  "quote_low": 11.34, "quote_high": 25.34, "price_band": "100-200", "band_mae": 7.0,
  "tariff": 15.88,
  "check": {
    "charged": 35.0, "excess": 16.66, "markup": 1.91, "log_ratio": 0.6215, "audit_band": "100-200",
    "rules": {
      "overall": {"label": "Top 5% overall (evaluated)", "forest": false, "ridge": false, "verdict": "normal"},
      "band": {"label": "Top 5% within each price band (recommended)", "forest": false, "ridge": false,
               "verdict": "normal"}
    }
  },
  "inputs": {"weight_kg": 1.5, "volume_cm3": 9000.0, "chargeable_kg": 1.8, "distance_km": 362.9, "same_state": 0,
             "price": 120.0, "n_items": 1, "n_sellers": 1, "seller_state": "SP", "customer_state": "RJ",
             "category": "bed_bath_table"},
  "notes": [], "drift_warnings": []
}
```
- `quote_low`/`quote_high`: fair freight ± the forest's test MAE for items in the same price band.
- `check.rules`: a charge is **unusual** when log(1 + charged) − log(1 + fair) is in the top 5% of the test set:
  overall (`overall`, the rule the notebooks evaluate: 1,128 test items) or within each price band (`band`, the rule
  the report recommends: 1,129 items, so expensive items do not crowd the list). `verdict` is `unusual_both` (forest
  and Ridge agree: review first), `unusual_forest_only` or `normal`.
- `tariff`: what the simple published tariff (R$ 9.61 + 1.846 per chargeable kg + 0.811 per 100 km − 3.985 within a
  state) would charge; `null` when the distance is unknown.

### POST /freight/batch

```bash
curl -X POST $API/freight/batch -H "Content-Type: application/json" -d '{"items": [
  {"price": 120, "weight_kg": 1.5, "volume_cm3": 9000, "seller_state": "SP", "customer_state": "RJ", "freight_value": 35},
  {"price": 45, "weight_kg": 0.3, "volume_cm3": 1500, "seller_state": "SP", "customer_state": "BA", "freight_value": 12}]}'
```
```python
items = [{"price": 120, "weight_kg": 1.5, "volume_cm3": 9000, "seller_state": "SP", "customer_state": "RJ"},
         {"price": 45, "weight_kg": 0.3, "volume_cm3": 1500, "seller_state": "SP", "customer_state": "BA"}]
res = requests.post(f"{API}/freight/batch", json={"items": items}, timeout=300).json()
res["n"], res["n_with_drift"], [p["fair_freight"] for p in res["predictions"]]
```
The response holds `request_id`, `timestamp`, `latency_ms`, `n`, `n_with_drift` and `predictions`, one object per
item in the order sent, each shaped like the single response above. A batch takes 1 to 5,000 rows; send larger files
in chunks (see `batch_score.py`). One invalid row rejects the whole batch with a 422 that names the row
(`items.3.price: ...`), so a client can drop it and resend.

### POST /late/predict (Problem 2)

| Field | Required | Rule |
|---|---|---|
| `promised_days` | yes | promised delivery time in days from purchase, > 0, ≤ 365 |
| `price_total` | yes | order value, all items, > 0 |
| `freight_total` | yes | freight charged, all items, ≥ 0 |
| `seller_state`, `customer_state`, `seller_zip`, `customer_zip`, `distance_km` | as above | |
| `n_items`, `n_sellers` | no | default 1 |
| `id` | no | echoed back |
| `?share=` (query) | no | review capacity, 0.01 to 0.5, default 0.10: `on_review_list` is true when the order is in the riskiest `share` of test-window orders |

```bash
curl -X POST "$API/late/predict?share=0.1" -H "Content-Type: application/json" -d '{
  "id": "order-1", "promised_days": 12, "price_total": 150, "freight_total": 25,
  "seller_state": "SP", "customer_state": "BA"}'
```
```python
order = {"id": "order-1", "promised_days": 12, "price_total": 150, "freight_total": 25,
         "seller_state": "SP", "customer_state": "BA"}
p = requests.post(f"{API}/late/predict", json=order, params={"share": 0.1}, timeout=90).json()
print(p["risk"], p["percentile"], p["on_review_list"], p["suggested_follow_up"])
```
Response (abridged):
```json
{
  "request_id": "req_20261029_064650_bfb569", "latency_ms": 20.3, "id": "order-1",
  "risk": 0.4851, "percentile": 99.3, "on_review_list": true, "share": 0.1,
  "drivers": {"promised_days": 0.870, "distance_km": 0.484, "same_state": 0.206, "price_total": 0.032,
              "freight_total": 0.096, "freight_ratio": -0.009, "n_items": 0.041, "n_sellers": 0.030,
              "seller_state": 0.149, "customer_state": 0.617},
  "top_driver": "promised_days", "suggested_follow_up": "Check carrier tracking",
  "inputs": {"promised_days": 12.0, "distance_km": 1430.2, "same_state": 0, "price_total": 150.0,
             "freight_total": 25.0, "freight_ratio": 0.1667, "n_items": 1, "n_sellers": 1,
             "seller_state": "SP", "customer_state": "BA"},
  "notes": ["Distance measured from the seller's centre of SP to the customer's centre of BA."],
  "drift_warnings": []
}
```
- `risk` is a ranking score, not a calibrated probability; `percentile` places it among the 19,295 test-window orders.
- `drivers`: each input's push on the log-odds of lateness against the average test-window order (the one-hot
  columns of each state are summed). The suggested follow-up comes from the group that pushes the risk up most:
  promise → *Update the delivery estimate*; route → *Check carrier tracking*; order size and value → *Confirm
  dispatch with seller*; none → *Send a tracking update*.

### Errors

Invalid input never reaches the models. Pydantic checks types, required fields and ranges, and custom validators
check states, zip codes and `n_sellers ≤ n_items`. The API answers **422** with FastAPI's standard `detail` plus one
readable line per problem in `errors`:

```bash
curl -X POST $API/freight/predict -H "Content-Type: application/json" \
  -d '{"price": 0, "weight_kg": 1.5, "volume_cm3": 9000, "seller_state": "XX", "customer_state": "RJ"}'
```
```json
{"detail": [{"type": "value_error", "loc": ["body", "seller_state"], "msg": "..."},
            {"type": "greater_than", "loc": ["body", "price"], "msg": "Input should be greater than 0"}],
 "errors": ["seller_state: 'XX' is not a Brazilian state code (two letters, such as SP; see /model-info)",
            "price: Input should be greater than 0"],
 "hint": "See /docs for the expected fields and their ranges."}
```
Other cases: a malformed zip (`'12' is not a zip code: give the CEP (e.g. 01310-100) or its first five digits`), a
missing field (`promised_days: Field required`), a batch over 5,000 rows (`... split the rows into batches of at most
5,000`). Unknown extra fields are ignored and listed in `notes`.

## Drift warnings

`models/feature_stats.json` (written by `build_models.py` from the training splits) holds the training mean and
standard deviation of every numeric input. An input is flagged when it lies **more than 3 standard deviations from
its training mean**. Weights, volumes, distances, prices and freight are compared on the log1p scale, as the linear
models see them, so both tails are covered; counts of items and sellers (mostly 1) are flagged only above the
training maximum; categories and states the model never saw in training are flagged too. Example:

```json
"drift_warnings": ["weight_kg = 60.00 is above the training mean + 3 sd on the log scale (18.31): the model has seen few cases like this"]
```
About 4% of the held-out test records get a warning. A warning does not block the prediction: it says the model is
extrapolating, so the result needs care.

## Inference log

Every prediction is appended to `logs/predictions.jsonl`, one JSON object per line: `timestamp`, `request_id`,
`endpoint`, `row`, `input`, `outputs` (fair freight and verdicts, or risk, percentile, review-list flag and
follow-up), `has_drift`, `drift_inputs`, `drift_warnings` and `latency_ms`. Rejected requests are logged with their
errors. `/logs/summary` aggregates the log; the totals are kept in memory and rebuilt from the file at startup. Read
the file with `pandas.read_json("logs/predictions.jsonl", lines=True)`.

## Bulk scoring

- `batch_score.py` scores every held-out record through the API, in chunks of 2,000, and writes the files the
  Streamlit app's population pages read (`deployment/model_app/data/scored_items.csv` and `scored_orders.csv`). It
  then checks the API against the pipelines run locally (forest within 1e-9 on the log scale, the others to 1e-9)
  and every unusual-freight and review-queue count in `facts.json`; it writes nothing if a check fails.
  ```bash
  pip install -r deployment/api/requirements-dev.txt
  python deployment/api/batch_score.py --api https://team5-olist-api.onrender.com
  ```
- `bulk_scoring_demo.ipynb` shows the same idea step by step (like the lesson's L6.2): a loop of single calls, then
  one batch call, results in a DataFrame.

## Run and test locally

From the repository root:
```bash
pip install -r deployment/api/requirements-dev.txt
uvicorn main:app --app-dir deployment/api --reload          # http://localhost:8000/docs
cd deployment/api && python -m pytest -q                    # 32 tests with FastAPI's TestClient
```
The Streamlit app reads the API address from `st.secrets["API_URL"]`, then the `API_URL` environment variable, and
defaults to the Render service; to use a local API: `API_URL=http://localhost:8000 streamlit run deployment/model_app/app.py`.

## Deploy on Render

1. Push this repository (it is public, so Render's free tier can read it).
2. On https://render.com choose **New → Web Service**, connect the GitHub repository and set:

| Setting | Value |
|---|---|
| Branch | `Phase3_Test` |
| Root directory | `deployment/api` |
| Runtime | Python 3 (version from `.python-version`: 3.12.7) |
| Build command | `pip install -r requirements.txt` |
| Start command | `uvicorn main:app --host 0.0.0.0 --port $PORT` (as in the `Procfile`) |
| Instance type | Free (512 MB RAM, 0.1 CPU) |

3. When the log shows `Models loaded successfully!`, open `/docs`. If the service name differs from
   `team5-olist-api`, set `API_URL = "https://<name>.onrender.com"` in the Streamlit app's **Secrets**.

**Free-tier limits.** The service sleeps after 15 minutes without traffic and takes 30 to 60 seconds to wake; the
app shows a "waking the API" message and retries. The three pipelines take about 300 MB of the 512 MB, and the forest
predicts on one core. Local files are ephemeral, so the inference log restarts when the service sleeps or is
redeployed; production use would log to a database.
